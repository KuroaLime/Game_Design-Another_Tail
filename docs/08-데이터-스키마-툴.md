## 1. 목적

원본은 p.75에 스킬 테이블 하나만 스키마 형태로 정의했습니다. 그런데 지금까지 확정한 시스템들 — 적응형 AI, 카르마 4축, 속성 연쇄, 마법 내장 슬롯, 퀘스트 분기 — 은 전부 **데이터 주도(data-driven)로 만들지 않으면 밸런싱이 불가능한** 구조입니다.

이 문서는 세 가지를 합니다.

1. 01·02·07에 흩어진 스키마를 하나로 모으고, 빠진 테이블을 채운다
2. 그 데이터를 만들 **툴 5종**을 정의한다 — 원본 p.211의 `툴·파이프라인 중·상급 3명 × 30개월 (6.45억)` 의 근거
3. 데이터 볼륨을 산정한다 — [04 사업성](04-사업성-손익-계획.md)의 로컬라이제이션 견적 선행 조건

### 1.1 데이터 주도가 필수인 이유

| 시스템 | 조정 대상 수 | 하드코딩 시 |
|---|---:|---|
| 스킬 | 약 118개 × 18개 필드 | 계수 하나 바꿀 때마다 빌드 |
| 적응형 AI 대응 규칙 | 12건 × 개체군 수 | [01 §10 I-01/I-02](01-적응형-전투-AI.md#10-미해결-이슈)의 프로토타입 비교 실험 자체가 불가능 |
| 속성 · 상태이상 | 13 + 16 | [05 §10](05-데미지-공식-검증.md#10-파라미터-표) 파라미터 18종 |
| 퀘스트 분기 | 116개 + 플래그 | 분기 하나 추가에 코드 수정 |
| 카르마 행동값 | 약 60개 행동 | 밸런싱 반복 불가 |

## 2. 데이터 아키텍처

```
┌──────────────────────────────────────────────────────────────┐
│ 마스터 데이터 (읽기 전용, 빌드에 포함)                        │
│   Element / StatusEffect / ChainRule / Skill / Trait          │
│   Class / LevelCurve / Monster / MonsterGroup / AdaptRule     │
│   Item / Equipment / Socket / Recipe / DropTable              │
│   Stage / Encounter / Quest / ActionAxisValue / Companion     │
│   → 소스: 스프레드시트 · 툴 → 빌드 시 바이너리 변환           │
└──────────────────────────────────────────────────────────────┘
                            ↓ 참조
┌──────────────────────────────────────────────────────────────┐
│ 세이브 데이터 (플레이어별, 로컬 + 클라우드)                    │
│   CharacterState / Inventory / MasteryState                   │
│   ReputationState / BondState / WitnessEvent                  │
│   QuestState / FlagState / PlayerCombatProfile                │
└──────────────────────────────────────────────────────────────┘
                            ↓ 익명 집계
┌──────────────────────────────────────────────────────────────┐
│ 텔레메트리 (서버, 옵트인)                                     │
│   EncounterLog / ProgressionLog / ChoiceLog / UIEventLog      │
│   → [01 §8.1](01-적응형-전투-AI.md#81-kpi) KPI 측정용         │
└──────────────────────────────────────────────────────────────┘
```

> **텔레메트리가 백엔드 인력의 유일한 정당한 사유입니다.** [04 §6.1 C-1](04-사업성-손익-계획.md#61-삭감-후보)에서 네트워크·백엔드를 4명 → 1명으로 줄이자고 권고했는데, 그 1명이 담당하는 것이 이 계층 + 클라우드 세이브 + 도전과제입니다.

  sp_cost         int              -- sp_purchase 일 때 (06 §2.4 총 60점)
